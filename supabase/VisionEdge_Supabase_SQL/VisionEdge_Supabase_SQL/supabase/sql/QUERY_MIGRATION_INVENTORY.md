## Additional observations

- Static scan found 23 SQLAlchemy model classes in `backend/models.py`: User, Customer, CustomerProfile, Appointment, EyeTest, Prescription, Frame, Lens, Supplier, Order, OrderItem, Billing, Payment, LensRecommendation, FrameRecommendation, VirtualTryOnHistory, ChatHistory, Notification, AuditLog, Brand, Category, InventoryTransaction, OrderStatusHistory.
- 52 non-venv Python files were found under `backend/`; route/helper files with ORM/raw-query usage are listed above. The ZIP contains a large virtual environment, excluded from the application-source audit.
- No application code was edited. No SQL was run against MySQL, SQLite, or Supabase.
- SQL table names follow SQLAlchemy default lowercase naming conventions, including `user`, `customer_profile`, `order_item`, `virtual_try_on_history`, and `order_status_history`.
- `OrderItem.product_id`/`item_id` and `InventoryTransaction.product_id` are polymorphic in the existing design; the schema cannot safely enforce a single FK target.
- `Brand` and `Category` are compatibility models; current `Frame` and `Lens` store brand/category as text and do not define relationships to those tables.
- The models do not declare a dedicated `Appointment` owner user, explicit payment provider table, or explicit supplier-to-product FK.
- RLS policies cannot be safely tied to Flask JWT claims from the source as inspected; a policy design requires an explicit identity propagation architecture.
- The app has duplicated blueprint registrations under plural and singular URL prefixes; this is an application concern, not a schema change.
- `db.create_all()` in `app.py` means the application may attempt automatic schema creation on startup when run directly. Manual SQL and this behavior should be reconciled by the project owner.
